Fundamentos · Qué es SDD

¿Qué es Spec-Driven Development?

El cambio de paradigma: pasar del prompt engineering caótico al contrato formal ejecutable.

El Problema del Prompt Libre

Pedir código directamente a un agente genera soluciones inconsistentes, código no solicitado y asunciones erróneas de arquitectura.

La Especificación como Blueprint

Antes de tocar código, se formaliza la intención de negocio en un contrato estructurado (objetivo, deltas, escenarios y tareas).

El Agente como Ejecutor Guiado

El LLM ya no adivina el alcance: lee la spec, escribe el test que falla y produce el cambio exacto con cero código fantasma.

💡 Definición Clave: SDD es la disciplina de usar especificaciones formales y versionadas en Git como la única fuente de verdad que guía el ciclo de vida de los agentes de IA.

Fundamentos · Pilares de Diseño

Los Tres Pilares de una Spec Real

Una definición técnica, auditable y determinista para ingeniería de software.

1. Ejecutable

El agente consume la spec por CLI para derivar el plan técnico y los casos de prueba sin interpretación subjetiva.

2. Verificable

Cada requisito define escenarios WHEN / THEN vinculados 1:1 con métodos de test en JUnit / Playwright.

3. Efímera en Tránsito

El cambio vive en changes/<id> durante el PR y se fusiona atómicamente en specs/ al mergear.

🧪 La Prueba Ácida de una Especificación Senior Benchmark

"Si eliminás el archivo de especificación y el equipo sigue trabajando exactamente igual, entonces nunca fue una spec: era solo documentación decorativa."

Las Herramientas · Comparativa

OpenSpec vs. GitHub SpecKit

Dos filosofías distintas para gobernar el desarrollo asistido por IA.

Dimensión OpenSpec (Fission-AI) GitHub SpecKit (GitHub)
Modelo Mental Deltas en Filesystem: ADDED, MODIFIED, REMOVED. Expediente Completo: Spec, Research, Data Model, Contracts.
Impacto en Review Micro-Deltas: 40-60 líneas auditables en 5 min. Dossier Completo: 200+ líneas de análisis y decisiones.
Estructura changes/<id> (efímero) ➔ specs/ (vivo y fusionado). specs/<id>-feature/ (expediente histórico estático).
Ideal Para... Brownfield, refactoring, micro-PRs frecuentes. Greenfield, dominios regulados (banca/salud), alta ambigüedad.

El Origen del Test: Tradicional vs SDD Shift Left
🔴 Flujo Vicioso Tradicional:
Ticket ➔ Código Intuitivo ➔ Test desde Código ➔ CI Verde Falso
🟢 Flujo Spec-Driven (SDD):
Regla ➔ Spec (WHEN/THEN) ➔ Test RED ➔ Código GREEN ➔ CI Real

Principio Fundamental: SDD no inventa burocracia; desplaza el origen del test hacia el contrato formal ejecutable.

Gobernanza Operativa · CONSTITUTION §6

Los 5 Quality Gates y Preflight Local

Paradas duras: ningún código progresa sin satisfacer el 100% de las condiciones del gate.

Quality Gate Condición de Bloqueo (Hard Stop) Herramienta de Control
Gate 1 (Plan) No implementar sin Issue abierto en GitHub + Spec + Acceptance Criteria. validate-sdlc-plan.sh ↗
Gate 2 (TDD) No escribir código antes de ver los Unit & Integration Tests fallar (RED). mvn test -pl backend-api
Gate 3 (Pre-PR) Suite completa en verde + Cobertura JaCoCo ratchet 80% + Spotless clean. preflight.sh --fix ↗
Gate 4 (Merge) CI/CD 100% verde + Aprobación de Code Owner en PR. GitHub Actions (ci.yml)
Gate 5 (Done) Deploy exitoso en Docker + Smoke test verificado ➔ Cerrar Issue. cd.yml + Smoke verification
Escalabilidad en Equipo · Concurrencia

Concurrencia y Deltas en Paralelo

Cómo escalar OpenSpec en monorepos con múltiples desarrolladores y agentes concurrentes.

1. Aislamiento por Rama

Cada cambio tiene su propia rama <type>/<issue>_<desc> y su subcarpeta aislada en openspec/changes/<name>.

2. Rebase Pre-Apply

Antes de /opsx:apply, se actualiza la rama con git pull origin main --rebase para sincronizar specs/ maestras.

3. Fusión en Archive

Al mergear el PR, /opsx:archive fusiona secuencialmente el delta en specs/, garantizando cero conflictos de historial.

🛡️ Regla de oro: Las especificaciones maestras en openspec/specs/ nunca se editan a mano; se actualizan automáticamente al archivar cambios aprobados.

Anti-Patrones & Soluciones

Trampas Comunes en Adopción de SDD

Los 3 errores más frecuentes en equipos y cómo Notaire los previene mecánicamente.

1. El Olvido de Archivar

Problema: El desarrollador mergea el código pero olvida correr /opsx:archive, dejando specs/ desactualizado.
Solución: Gate 5 en CI bloquea el cierre del ticket si changes/ no fue archivado.

2. Aserciones Debilitadas

Problema: El agente debilita el test para forzar el verde en lugar de corregir la lógica.
Solución: Code review audita el delta de la spec contra los métodos de prueba con AssertJ.

3. Desfase de Spotless/Linter

Problema: mvn verify pasa pero CI falla en formateo.
Solución: Pre-push hook ejecuta obligatoriamente bash scripts/preflight.sh --fix.

Del Delta al Código: Ciclo TDD Completo

Resolución de la rama fix/848_reject-payments-exceeding-saldo.

1. Delta Spec proposal.md en GitHub ↗ 
## MODIFIED Requirements

### Requirement: Validación de Monto Máximo
El sistema SHALL rechazar cualquier pago cuyo monto
supere el saldo pendiente del presupuesto.

#### Scenario: Rechazar sobrepago
- WHEN se recibe pago con monto > saldo pendiente
- THEN arroja BusinessException(409 Conflict)
- AND ningún registro es persistido
2. Implementación TDD PagoService.java en GitHub ↗ 
public Pago procesarPago(Integer idPresupuesto, Float monto...) {
    Float saldo = calcularSaldoPendiente(idPresupuesto);
    if (monto > saldo) {
        throw new BusinessException(
            "El monto excede el saldo pendiente ($" + saldo + ")"
        );
    }
    return pagoRepository.save(pago);
}

Visión de Futuro · Siguientes Pasos

Memoria Compartida & Base de Conocimiento

Transformando las especificaciones vivas en la inteligencia colectiva del equipo.

1. Búsqueda Semántica (RAG)

Indexación vectorial de specs/, ADRs y changes/archive/ para consultas en lenguaje natural sobre decisiones de arquitectura pasadas.

2. Continuous Feedback Loop

Los agentes aprenden de los PRs mergeados anteriores: patrones de diseño, nombres de métodos y reglas notariales sin re-prompting manual.

3. Onboarding & Auditoría

Cualquier nuevo desarrollador o auditor pregunta a la memoria corporativa el por qué de una regla y obtiene la spec exacta y el commit que la originó.

🧠 El Valor Definitivo de SDD: El código ejecuta el presente; las especificaciones indexadas preservan el razonamiento histórico de toda la organización.
