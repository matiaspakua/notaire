1 · Foundations

What is Spec-Driven Development?

Executable specifications that guide code generation, instead of ad-hoc prompts.

✗ Without SDDAd-hoc prompting
$ "add an endpoint to re-file
   documentation; look at how
   the rest is built"
  • The agent rebuilds the context from scratch every time
  • No record of why a decision was made
  • Each feature drifts a little from the rest
  • Review depends on human memory, not on artifacts
✓ With SDDExecutable specification
# spec.md
User Story: Re-file documentation
Acceptance: Given/When/Then
Traceability: Issue #865 · CU-43
  • The spec is the source of truth, not the prompt
  • The code is derived from it and checked against it
  • Traceability Issue → Use Case (Caso de Uso) → Tests → PR
  • Architectural consistency across different features
1 · Foundations

Problems SDD solves with AI agents

It is not bureaucracy — it is what makes it possible to delegate real work to an agent without losing control.

🤝
Human/AI alignment

The spec is reviewed before writing code — disagreement shows up in text, not in a 40-file diff.

🔗
Traceability

Issue → Use Case (Caso de Uso) → Spec → Tests → Commit → PR. Every line of code explains where it came from.

🏛️
Architectural consistency

Every spec inherits the same rules (CONSTITUTION.md) — two features do not use different conventions.

⚡
Menos "context tax"

The agent does not rebuild context from the code every time — it reads it from versioned, compact artifacts.

2 · Frameworks

OpenSpec vs GitHub Spec Kit

Two different philosophies — Notaire uses both, each where it fits best.

🌱 OpenSpecBrownfield
  • Philosophy: incremental change on existing code
  • Spec model: delta specs (ADDED / MODIFIED / REMOVED)
  • Typical fit: fixes and small or medium features on a living system
  • Cycle: /opsx:explore → propose → apply → verify → archive
  • Strong at: small, auditable PRs and low documentation overhead
🌳 GitHub Spec KitGreenfield
  • Philosophy: an exhaustive specification before touching code
  • Spec model: a complete spec.md with prioritized User Stories
  • Typical fit: new features, complete subsystems
  • Cycle: constitution → specify → plan → tasks → implement
  • Strong at: Socratic clarification and exhaustive design before coding

The 5 commands
  • /opsx:explore — maps the problem and understands the existing codebase
  • /opsx:propose — drafts proposal.md, specs/ (delta), design.md, and tasks.md
  • /opsx:apply — implements the tasks against the specification
  • /opsx:verify — checks that the implementation matches the spec
  • /opsx:archive — archives the completed change and merges the delta
3 · Practical case A — Brownfield

Delta specs and the advantages on existing codebases

Delta specs
ADDED — new capability MODIFIED — an existing capability changes REMOVED — a capability is retired

On /opsx:archive, the delta merges into openspec/specs/ — the permanent spec stays current.

Lower overhead

4 files instead of 7+ — proportional to the real size of the change, without skipping Gates 1–5. You do not re-specify the whole module to fix a badly mapped type: the delta describes only what changes.

4 · Practical case B — Greenfield

Artifact layout (7+ files per feature)

📁 docs/000-archive/speckit/specs/<NNN-feature>/
spec.md          # User Stories + Given/When/Then
plan.md          # Technical design, contracts
tasks.md         # Gates 1–12 + phases per user story
traceability.md  # Issue, CU, branch, PRs
research.md      # Technical decisions (optional)
data-model.md    # New entities (optional)
contracts/       # OpenAPI for new endpoints
checklists/      # Checklist de requirements
Typical deliverables
  • User Stories with priority (P1/P2) and an "Independent Test"
  • A "Verified starting point" section — what already exists, what is missing
  • Tasks grouped by Gate and by User Story ([P] means parallelizable)
  • Traceability with Issue, Use Case (Caso de Uso), and branch from day one
⚠️ Enterprise reality

They do not fail because of the method — they fail for lack of coupling

OpenSpec and Spec Kit assume a clean environment. A real company (Jira, GitHub, Confluence, compliance) needs integration and context layers.

Framework default
→
Legacy / enterprise reality
→
Adjustments required
→
Usable result
📋 Jira

The real source of the work.

Adjustment: ticket → spec.

🐙 GitHub

Protected branches, CI, CODEOWNERS.

Adjustment: branch/PR from the spec.

📚 Confluence

Scattered knowledge (ADRs, standards).

Adjustment: inject context into the plan.

🖥️ Dev environments

"It works on my machine" is the norm.

Adjustment: bootstrap + Docker.

🔒 Compliance

Security, PII, audit.

Adjustment: explicit gates.

Without adjustments: misaligned specs → unrealistic plans → rejected PRs. With adjustments: real adoption — there is no adoption without translating between the framework and the socio-technical system.

When to use each framework?

SituationRecommendation
A targeted fix on existing code (such as #879)OpenSpec — a small delta, MODIFIED/ADDED
A new end-to-end feature, a whole use case (such as #865)Spec Kit — User Stories + an exhaustive plan
A new module from scratch, with no prior codeSpec Kit — constitution → specify → plan
An incremental change on a living subsystemOpenSpec — living specs, low overhead
Needs Socratic clarification before codingSpec Kit — a dedicated /clarify step
A small, auditable PR, mergeable in hoursOpenSpec — 4 artifacts, a short cycle
5 · Close

Team adoption pattern

1
Pilot

One developer or agent tries the framework on 1–2 small real changes. Friction is measured; it is not imposed yet.

2
Minimum standards

Recorded in CONSTITUTION.md: mandatory gates, naming, and where each artifact lives.

3
Progressive rollout

The whole team (humans and AI agents) uses it by default. Exceptions are documented and explicit.

SDD is not more process.
It is less ambiguity per PR.

Two frameworks, one close: CONSTITUTION.md Gate 5. Choose the one that matches the size of the change.
