1 · Fundamentos

¿Qué es Spec-Driven Development?

Especificaciones ejecutables que guían la generación de código, en lugar de prompts ad-hoc.

✗ Sin SDDAd-hoc prompting
$ "agregá un endpoint para reingresar
   documentación, fijate cómo está
   armado el resto"
  • El agente reconstruye el contexto desde cero cada vez
  • Sin registro de por qué se decidió algo
  • Cada feature diverge un poco del resto
  • La review depende de memoria humana, no de artefactos
✓ Con SDDEspecificación ejecutable
# spec.md
User Story: Reingresar documentación
Acceptance: Given/When/Then
Traceability: Issue #865 · CU-43
  • La spec es la fuente de verdad, no el prompt
  • El código se deriva y se valida contra ella
  • Trazabilidad Issue → Caso de Uso → Tests → PR
  • Consistencia arquitectónica entre features distintas
1 · Fundamentos

Problemas que resuelve SDD con agentes de IA

No es burocracia — es lo que hace posible delegar trabajo real a un agente sin perder control.

🤝
Alineación humano/IA

La spec se revisa antes de escribir código — el desacuerdo se detecta en texto, no en un diff de 40 archivos.

🔗
Trazabilidad

Issue → Caso de Uso → Spec → Tests → Commit → PR. Cada línea de código explica de dónde vino.

🏛️
Consistencia arquitectónica

Todas las specs heredan las mismas reglas (CONSTITUTION.md) — no hay dos features con convenciones distintas.

⚡
Menos "context tax"

El agente no reconstruye contexto desde el código cada vez — lo lee de artefactos versionados y compactos.

2 · Marcos de trabajo

OpenSpec vs GitHub Spec Kit

Dos filosofías distintas — Notaire usa ambas, cada una donde mejor encaja.

🌱 OpenSpecBrownfield
  • Filosofía: cambio incremental sobre código existente
  • Modelo de spec: delta specs (ADDED / MODIFIED / REMOVED)
  • Encaje típico: fixes, features chicas/medianas sobre un sistema vivo
  • Ciclo: /opsx:explore → propose → apply → verify → archive
  • Fuerte en: PRs pequeños, auditables, bajo overhead documental
🌳 GitHub Spec KitGreenfield
  • Filosofía: especificación exhaustiva antes de tocar código
  • Modelo de spec: spec.md completo con User Stories priorizadas
  • Encaje típico: features nuevas, subsistemas completos
  • Ciclo: constitution → specify → plan → tasks → implement
  • Fuerte en: clarificación socrática, diseño exhaustivo antes de codear

3 · Caso práctico A — Brownfield

Flujo recomendado con OpenSpec

/opsx:explore → /opsx:propose → /opsx:apply → /opsx:verify → /opsx:archive — modelo de delta specs.

Los 5 comandos
  • /opsx:explore — mapea el problema y entiende el codebase existente
  • /opsx:propose — redacta proposal.md, specs/ (delta) y design.md, tasks.md
  • /opsx:apply — implementa las tasks contra la especificación
  • /opsx:verify — chequea que la implementación coincide con la spec
  • /opsx:archive — archiva el cambio completado, mergea el delta
3 · Caso práctico A — Brownfield

Delta specs y ventajas en codebases existentes

Delta specs
ADDED — capability nueva MODIFIED — capability existente cambia REMOVED — capability se retira

Al hacer /opsx:archive, el delta se mergea en openspec/specs/ — la spec permanente queda viva y al día.

Menor overhead

4 archivos en vez de 7+ — proporcional al tamaño real del cambio, sin sacrificar Gate 1-5. No hay que re-especificar todo el módulo para arreglar un tipo mal mapeado: el delta describe solo lo que cambia.

4 · Caso práctico B — Greenfield

Estructura de artefactos (7+ archivos por feature)

📁 speckit/specs/<NNN-feature>/
spec.md          # User Stories + Given/When/Then
plan.md          # Diseño técnico, contratos
tasks.md         # Gates 1-12 + fases por US
traceability.md  # Issue, CU, branch, PRs
research.md      # Decisiones técnicas (opcional)
data-model.md    # Entidades nuevas (opcional)
contracts/       # OpenAPI de endpoints nuevos
checklists/      # Checklist de requirements
Entregables típicos
  • User Stories con prioridad (P1/P2) y "Independent Test"
  • Sección "Verified starting point" — qué ya existe, qué falta
  • Tasks agrupadas por Gate + por User Story ([P] paralelizables)
  • Traceability con Issue, Caso de Uso y branch desde el día 1
⚠️ Realidad enterprise

No fallan por la metodología — fallan por falta de acoplamiento

OpenSpec y Spec Kit asumen un entorno limpio. La empresa real (Jira, GitHub, Confluence, compliance) exige capas de integración y contexto.

Framework default
→

→
Ajustes necesarios
→
Resultado usable
📋 Jira

Fuente real del trabajo.

Ajuste: ticket → spec.

🐙 GitHub

Ramas protegidas, CI, CODEOWNERS.

Ajuste: branch/PR desde spec.

📚 Confluence

Conocimiento disperso (ADRs, normas).

Ajuste: inyectar contexto al plan.

🖥️ Ambientes dev

"Funciona en mi máquina" es la norma.

Ajuste: bootstrap + Docker.

🔒 Compliance

Seguridad, PII, auditoría.

Ajuste: gates explícitos.

Sin ajustes: specs desalineadas → planes irreales → PRs con rechazo. Con ajustes: adopción real — no hay adopción sin traducción entre el framework y el sistema socio-técnico.

5 · Cierre

¿Cuándo usar cada framework?

SituaciónRecomendación
Fix puntual sobre código existente (como #879)OpenSpec — delta chico, MODIFIED/ADDED
Feature nueva end-to-end, un CU completo (como #865)Spec Kit — User Stories + plan exhaustivo
Módulo nuevo desde cero, sin código previoSpec Kit — constitution → specify → plan
Cambio incremental sobre subsistema vivoOpenSpec — living specs, bajo overhead
Requiere clarificación socrática antes de codearSpec Kit — paso /clarify dedicado
PR chico, auditable, mergeable en horasOpenSpec — 4 artefactos, ciclo corto
5 · Cierre

Patrón de adopción en equipos

1
Pilotaje

Un dev/agente prueba el framework en 1-2 cambios reales chicos. Se mide fricción, no se impone todavía.

2
Estándares mínimos

Se documenta en CONSTITUTION.md: Gates obligatorios, nomenclatura, dónde vive cada artefacto.

3
Extensión progresiva

Todo el equipo (humano + agentes IA) lo usa por defecto. Excepciones documentadas y explícitas, no silenciosas.

SDD no es más proceso.
Es menos ambigüedad por PR.

Dos frameworks, un mismo cierre: CONSTITUTION.md Gate 5. Elegí el que corresponda al tamaño del cambio, no al gusto del día.
