🎯¿Qué es Spec-Driven Development?

Definición: Especificaciones ejecutables que guían la generación de código en lugar de prompts ad-hoc.

Por qué importa con Agentes de IA

  • ✅ Alineación humano-IA: El agente y el humano hablan el mismo lenguaje formal
  • ✅ Trazabilidad completa: Desde Requerimiento → Spec → Test → Código → PR
  • ✅ Consistencia arquitectónica: Evita desviaciones del diseño
  • ✅ Reducción de "context tax": Menos prompts, más confianza

🔧Problemas que Resuelve SDD

❌ Sin SDD (Prompts Ad-hoc)

  • Especificaciones implícitas
  • Cambio de contexto frecuente
  • Pruebas desalineadas
  • Documentación fragmentada
  • Presión en code review

✅ Con SDD (Specs Ejecutables)

  • Requerimientos formales y verificables
  • Contexto persistente y reutilizable
  • Tests diseñados en paralelo
  • Especificaciones vivas
  • Code review más ágil
Impacto en equipos: Menos "ping-pong" IA-humano, decisiones documentadas desde el inicio, refactors de bajo riesgo.

⚙️Dos Frameworks, Dos Filosofías

📦 GitHub SpecKit

Filosofía: Documentación exhaustiva, socrática e interactiva.

  • Modelo: Dossier documental
  • Ciclo: Plan → Implement
  • Mejor para: Greenfield, equipos nuevos
  • Artefactos: 7+ por feature

🔄 OpenSpec

Filosofía: Deltas efímeros en filesystem, micro-PRs auditables.

  • Modelo: Specs vivos (ADDED/MODIFIED/REMOVED)
  • Ciclo: Propose → Apply → Archive
  • Mejor para: Brownfield, legado
  • Cambio incremental

📈Patrón de Adopción en Equipos

Fase 1: Pilotaje (1-2 semanas)

  • Seleccionar 1 feature representativa
  • Aplicar SpecKit (o OpenSpec) completo
  • Documentar learnings

Fase 2: Estándares Mínimos (2-4 semanas)

  • Todas las features nuevas siguen el framework
  • Revisión en CI/CD: Git hooks + validation scripts
  • Entrenar al equipo en herramientas

Fase 3: Extensión Progresiva (Ongoing)

  • Refactorings complejos usan SpecKit
  • Bugs críticos → OpenSpec delta
  • Specs se convierten en living documentation

📚 ANEXO

Faltante Crítico: Memory de Specs

💾Spec Memory: El Faltante Crítico

¿Qué es?

Sistema para persistir y compartir decisiones de specs entre:

  • 👤 Miembros del equipo (presente y futuro)
  • 🤖 Agentes de IA (contexto reutilizable)
  • 📖 Documentación viva (histórico de WHY)

Problema Actual

Specs se archivan después de PR → Contexto se pierde → 6 meses después: "¿Por qué decidimos así?" → Reescritura innecesaria

Solución Propuesta

  • Spec Memory File: `decisions.md` en cada módulo (ADDED/MODIFIED/REMOVED decisions)
  • AI Context Bridge: Agentes leen memory antes de proponer cambios
  • Team Wiki: Specs vivas + rationale en central location
