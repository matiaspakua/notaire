## Objetivo

Slice 1 (PR #2103) delivered the TOTP core but login is still password-only (OWASP A07). Slice 2 wires the policy into login: a confirmed enrolment turns a password login into a short-lived challenge, ROLE_ADMIN and ROLE_NOTARY must enrol when enforcement is on, and wrong codes feed the existing lockout. Stacked on feat/1640_mfa-totp-backend.

## What Changes

- Domain `domain.mfa`: `MfaPolicyMode`, `MfaLoginPolicy`, `LoginMfaDecision`; `domain.user.AccountRole` (single user-type to role mapping).
- Inbound ports `AssessLoginMfaUseCase`, `VerifySecondFactorUseCase`, `DisableTotpUseCase` and use cases in `application.usecase.mfa`.
- `POST /api/v1/users/login` returns an `mfaRequired` challenge (`valid=false`, scoped short-lived token) instead of a session when policy requires a second factor; new `POST /api/v1/users/login/mfa` verifies a TOTP or recovery code and only then issues the JWT.
- `POST /api/v1/mfa/enrollment`, `/enrollment/confirm`, `/disable` for the authenticated user only.
- Scoped JWTs (`mfa_challenge`, `mfa_enrollment`) that the session filter never accepts as a session.
- Wrong codes count in `LoginAttemptService` (lock + 429), logged and counted without code values.
- Property `notaire.mfa.policy` = OFF | OPTIONAL | ENFORCE, default OPTIONAL (recorded in ADR-032).

## Reglas de negocio

| Rule | Source | New / Changed / Made explicit |
|------|--------|-------------------------------|
| Under ENFORCE a ROLE_ADMIN or ROLE_NOTARY password login never yields a session token without a confirmed TOTP; under OPTIONAL a confirmed enrolment is honoured but nobody is forced; OFF disables the challenge | Issue #1640, ADR-032 decision 6, CU78 | New |
