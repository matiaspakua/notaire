# SpecKit ↔ Constitution Bridge

`CONSTITUTION.md` is the highest authority for how a change is made in this
repository (§12). Notaire already governs its spec-driven workflow with
**OpenSpec** (`openspec/`, schema `notaire-sdlc`, see
`openspec/NOTAIRE-ADAPTATIONS.md`). This document does
the same job for **GitHub Spec-Kit** (`specify` CLI), adopted here as an
alternative framework to evaluate side by side with OpenSpec — see
`speckit/EVALUATION.md` for the comparison grounded in the 3 evidence
features built through this adapted flow.

Everything SpecKit-related lives under this `speckit/` directory. It never
touches `openspec/`, and OpenSpec's process for existing changes is
unaffected.

## Analysis

### SpecKit's native structure

`specify init` scaffolds:

- `.specify/memory/constitution.md` — a single free-form "project
  constitution" file, filled interactively via `/speckit.constitution`.
- `.specify/templates/{spec,plan,tasks,checklist}-template.md` — vendor
  templates, expected to be regenerated by `specify upgrade`.
- `.claude/skills/speckit-*/SKILL.md` — the workflow commands:
  `/speckit-constitution` → `/speckit-specify` → `/speckit-clarify`
  (optional) → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze`
  (optional) → `/speckit-implement`, plus `/speckit-checklist` and
  `/speckit-converge`.
- `specs/NNN-feature-name/{spec.md,plan.md,tasks.md}` — created per feature
  on first `/speckit-specify` run, numbered sequentially.

SpecKit's spec template already encodes Given/When/Then Acceptance
Scenarios per user story (SpecKit's own equivalent of OpenSpec's
`#### Scenario:` blocks) and a Constitution Check gate inside `plan.md`
that is meant to reference `.specify/memory/constitution.md`. `tasks.md` is
organized by user-story phase (Setup → Foundational → per-story
Tests-then-Implementation → Polish), not by SDLC stage — a different
methodology than OpenSpec's twelve fixed SDLC groups, but one that already
enforces TDD ordering per story.

### Gaps against the Notaire Constitution

1. **No mandatory Issue/Use-Case linkage.** `spec.md` has no field for a
   GitHub Issue or a Use Case reference — a feature could be specified with
   no traceable Issue at all, violating §4/Gate 1.
2. **No live verification.** Nothing stops an agent from typing a
   plausible-looking, non-existent Issue number, mirroring the exact
   OpenSpec problem `openspec/NOTAIRE-ADAPTATIONS.md` already solved.
3. **`plan.md` has no SDLC strategy sections.** No Testing, Regression,
   Playwright, Deployment, or Rollback Strategy — SpecKit's plan is
   architecture-only (Constitution Check, Project Structure, Complexity
   Tracking), not release-aware the way `design.md` is under
   `notaire-sdlc`.
4. **`tasks.md` has no SDLC gates.** SpecKit's phases stop at "Polish &
   Cross-Cutting Concerns" — there is no group for committing, opening a
   PR, deploying, or a Gate-5 smoke test/close-out, and no Definition of
   Done checklist.
5. **No traceability ledger.** SpecKit has nothing equivalent to
   OpenSpec's `traceability.md` — no artifact records the Issue → Spec →
   Plan → Tasks → Commits → PR → Merge → Release chain with real,
   non-pre-filled evidence (Constitution P4).
6. **No mechanical gate.** All of the above are, at best, advisory prose a
   skill might follow. Nothing fails the build if a feature is scaffolded
   incompletely.

These six gaps motivated the three project-owned pieces below — the same
"adapt, don't replace" approach Constitution P10 required for OpenSpec.

## The fix: three project-owned pieces, no vendor file assumed stable

1. **`speckit/.specify/memory/constitution.md`** — filled with a pointer to
   `CONSTITUTION.md` plus the same non-negotiables list used in
   `openspec/config.yaml`'s `context:` field (Issue+Use Case required, TDD,
   branch/commit conventions, Gate 3 requirements, Flyway rules, design-system
   rules, UI-endpoint traceability) — never a copy of the Constitution itself
   (P7/§8). `specify upgrade` can overwrite this file; re-apply it from this
   document (the content is reproduced in full in this repo's git history at
   the commit that introduced it — diff against `git log -p` for the exact
   text) after any upgrade.

2. **Project-owned template deltas** — `speckit/.specify/templates/
   {spec,plan,tasks}-template.md` were customized in place (same risk as
   OpenSpec's `openspec-explore`/`openspec-propose` skills: vendor-owned,
   reset on `specify upgrade`):
   - `spec.md`: a **Notaire Traceability** header table (GitHub Issue + Use
     Case), inserted before "User Scenarios & Testing". SpecKit's existing
     Given/When/Then Acceptance Scenarios already satisfy the "Acceptance
     Criteria as scenarios" requirement — no change needed there.
   - `plan.md`: five new mandatory sections appended — Testing Strategy,
     Regression Strategy, Playwright Strategy, Deployment Strategy, Rollback
     Strategy — the same set `design.md` requires in `notaire-sdlc`.
   - `tasks.md`: a **Notaire SDLC Gates** block wraps SpecKit's native
     phases instead of discarding them: "Gate 1 — Prerequisites" and "Crear
     branch" before Phase 1, and "Actualizar tests existentes", "Ejecutar
     regresión", "Ejecutar Playwright", "Gate 3 — Actualizar documentación
     permanente", "Commits atómicos", "Pull Request y validación CI",
     "Deploy", "Gate 5 — Smoke test y cierre", and a Definition of Done
     checklist after the last user story's phase. SpecKit's own
     Tests-then-Implementation phases per user story satisfy groups 3/4 of
     the OpenSpec twelve (TDD + Implementation) without needing to be
     renumbered — see the mapping table inside the template.
   - **New** `speckit/.specify/templates/traceability-template.md` — SpecKit
     has no native equivalent; this is the same shape as OpenSpec's
     `traceability.md`: Chain, Requirement coverage, Permanent documentation
     updated, Gate log, Exceptions.

   Because the mechanical gate (next point) does not depend on these
   templates surviving an upgrade, template drift after `specify upgrade`
   degrades ergonomics (an agent following a reset template would produce an
   incomplete plan), not enforcement — the script still catches it.

3. **`scripts/validate-speckit-plan.sh`** (project-owned bash, mirrors
   `scripts/validate-sdlc-plan.sh` section-by-section) — the actual gate,
   agent-agnostic:
   - Iterates `speckit/specs/*/` feature directories.
   - `spec.md`: Notaire Traceability header present, Issue number present
     and **live-verified via `gh issue view`** (same OPEN-state check as the
     OpenSpec script, same degraded-mode note when `gh` is unavailable), Use
     Case reference present, at least one Given/When/Then scenario.
   - `plan.md`: Testing/Regression/Playwright/Deployment/Rollback sections
     present.
   - `tasks.md`: all 12 mandatory groups present (matched against both the
     "Gate N —" headings and SpecKit's native phase headings, per the
     mapping table in the template), Definition of Done present, minimum
     checkbox count (anti-boilerplate check, same idea as the 12-checkbox
     floor in `validate-sdlc-plan.sh`).
   - `traceability.md`: same 5 sections as OpenSpec's, not pre-filled.
   - Non-zero exit on any failure; `--list` flag documenting Local
     check → Constitution reference, matching the existing script's UX.
   - Wired into `scripts/preflight.sh` (next to `sdlc plan validation`) and
     into `.github/workflows/pr-validation.yml` as a new `speckit-plan` job,
     mirroring the existing `sdlc-plan` job — added in the same PR per the
     CLAUDE.md rule that a new gate and its CI wiring ship together.
   - **`speckit/specs/archive/`** — once a feature's Issue is closed (PR
     merged), its directory moves to `speckit/specs/archive/`, mirroring
     `openspec/changes/archive/`. The validation loop skips the `archive`
     basename, so a shipped feature's Issue is no longer required to stay
     OPEN — without this, every subsequent push repo-wide fails once the
     first SpecKit feature merges and its Issue closes (found via #866,
     after CU03/#860 closed and blocked the CU10/#863 pre-push hook).
     The archive move only helps if someone actually performs it: #866
     fixed the symptom for CU03 but didn't make the step self-enforcing, so
     CU10/#863 regressed the exact same failure the moment its own PR
     merged. #868 closed that gap by making the archive move an explicit
     Gate 5 task (`tasks-template.md`) generated for every future feature,
     and by pointing the validator's own CLOSED-issue error message at the
     fix instead of only documenting it in the script header.

This keeps the adaptation on the project side, per Constitution P10 ("Adapt,
don't replace"): SpecKit's vendor skills, templates, and scripts stay
installable/upgradable; the Constitution's requirements are layered on
through project-owned files plus one already-wired mechanical gate.

## Sequence

```text
        /speckit-specify           /speckit-plan            /speckit-tasks
Issue ───▶ spec.md cites ───▶ plan.md adds SDLC ───▶ tasks.md gets Notaire
(real,     REAL Issue +           strategy sections        SDLC Gates block
open)      Use Case                                        wrapped around
                                                             SpecKit's phases
                                        │
                                        ▼
                          scripts/validate-speckit-plan.sh
                          resolves Issue live via `gh issue
                          view` — fabricated or closed Issue
                          fails Gate 1; missing plan/tasks
                          sections fail too
```

## SpecKit ↔ OpenSpec artifact mapping

| SpecKit | OpenSpec | Notes |
|---|---|---|
| `spec.md` | `proposal.md` + `specs/*.md` deltas | SpecKit merges "what/why" and "acceptance scenarios" into one file |
| `plan.md` | `design.md` | Both now carry the same 5 SDLC strategy sections |
| `tasks.md` | `tasks.md` | SpecKit organizes by user story, OpenSpec by SDLC stage; both wrap the same 12 mandatory groups |
| `traceability.md` (new) | `traceability.md` | Identical shape, project-owned in both frameworks |
| `.specify/memory/constitution.md` | `openspec/config.yaml` `context:` | Both are pointers + non-negotiables, never a copy of `CONSTITUTION.md` |
| `scripts/validate-speckit-plan.sh` | `scripts/validate-sdlc-plan.sh` | Same checks, same `gh`-backed live Issue verification |

## Verification (2026-08-28)

Tested directly against `scripts/validate-speckit-plan.sh` using a scratch
fixture copied momentarily into `speckit/specs/000-scratch-fixture/` (never
committed):

| Case | Issue reference | Result |
|------|------------------|--------|
| Negative | `#999999` (does not exist) | ✗ `spec: Issue #999999 was not found on GitHub` — Gate 1 fails |
| Positive | `#857` (real, open — this tooling issue) | ✓ `spec: Issue #857 verified live on GitHub (OPEN)` |
| Degraded | `#857`, `gh` removed from `PATH` | `- spec: gh CLI not available/authenticated — Issue #857 not live-verified` (advisory, does not fail the gate) |

All three cases matched the OpenSpec script's behavior for the equivalent
checks in `openspec/NOTAIRE-ADAPTATIONS.md`.

## Evidence: three features carried through the adapted flow

Three Use Cases were built end to end through `/speckit.specify` →
`/speckit.plan` → `/speckit.tasks` → TDD → implement → PR, chosen to be
structurally distinct from every hallazgo already tracked in
`openspec/explore.md` (no overlap between the two tools' evidence):

| Feature | Use Case | Issue | PR | Status | Notes |
|---|---|---|---|---|---|
| Documentos y certificados necesarios por trámite | CU03 (#156) | #860 | [#861](https://github.com/matiaspakua/notaire/pull/861) | merged | New `TipoDeTramite`↔`TipoDeDocumento` link table (Flyway migration), printable checklist screen |
| Registrar movimientos de documentación de entidades externas | CU10 (#163) | #863 | [#864](https://github.com/matiaspakua/notaire/pull/864) | merged | External-entity document tracking, catastral nomenclature for `Inmueble`-linked gestiones |
| Reingresar documentación | CU43 (#196) | #865 | [#871](https://github.com/matiaspakua/notaire/pull/871) | open (CI/review pending) | Re-submission circuit for rejected/expired `DocumentoPresentado`; a Postgres-only regression test (`GestionReingresoDocumentacionPgIntegrationTest`) caught a NOT NULL gap H2's `ddl-auto=create` cannot enforce |

Two follow-up tooling fixes came directly out of running the flow for real,
not from the initial adaptation design — recorded here because they are the
concrete evidence that the mechanical gate (point 3 above) needed hardening
after first contact with a merged feature:

- **#866 → PR #867**: the first feature to merge (CU03/#860) closed its
  Issue, which then made `scripts/validate-speckit-plan.sh` fail for
  *every* subsequent push repo-wide, because the script required every
  `speckit/specs/*/` directory's Issue to still be `OPEN`. Fixed by moving
  the completed feature directory to `speckit/specs/archive/`, which the
  validator skips.
- **#868 → PR #869**: the archive move only helps if someone actually
  performs it — CU10/#863 hit the identical failure the moment *its* PR
  merged, because nothing made the move self-enforcing. Closed by making
  the archive move an explicit Gate 5 task in `tasks-template.md` for every
  future feature, and pointing the validator's own CLOSED-issue error
  message at the fix instead of only documenting it in the script header.
